# Output taxonomy — full field definitions

Load this when a categorization call in the main triage is ambiguous. For routine triage, the
table in SKILL.md is enough.

## Awareness stage

- **Problem-aware** — the audience doesn't yet know this gap has a name or is solvable. They're
  describing a symptom, not a category. Signal: the friction quote has no product/category
  vocabulary in it at all ("I just kind of guess," not "I wish our ASO tool did X"). These make
  the strongest pillar candidates because they're not yet owned by any competitor's messaging.
- **Solution-aware** — the audience knows the gap exists and has a name for it, and wants proof
  it can be solved or a path to act on it. Signal: they name the *problem category* but not a
  specific tool ("we need better keyword tracking," not "does Tool X do keyword tracking").
- **Product-aware** — actively comparing specific tools or vendors. Signal: they name tools,
  ask for feature comparisons, or describe a switching/evaluation process. These route toward
  comparison content or sales-facing material, not top-of-funnel blog pillars.

Misclassifying this is the most common error — a solution-aware cluster dressed up as
problem-aware produces a pillar piece that reads as if it's explaining something the audience
already knows, which reads as condescending rather than useful.

## Structural role

- **Pillar** — broad, evergreen, spans multiple sub-themes. Usually built from a recurring,
  problem-aware cluster. A pillar should be able to link out to 2+ supporting pieces; if you
  can't imagine what those supporting pieces would be, it's probably not actually pillar-scale.
- **Supporting** — narrower, answers one specific sub-question, links into a pillar (existing or
  planned). Most clusters land here.
- **Standalone** — self-contained, doesn't need a pillar to make sense (e.g. a timely reaction
  piece, a single case study, a product announcement). Don't force a standalone idea into a
  pillar/supporting relationship it doesn't have.

## Readiness

- **Ready to brief** — the cluster has enough source material and passes the compliance filter
  outright. Can go straight to the destination skill.
- **Gap** — strong signal (recurring across sources) but blocked on something specific: missing
  data, an internal alignment call, a product decision not yet made. Always name the blocker
  explicitly rather than just writing "Gap" — "Gap: waiting on Q3 benchmark data" is useful,
  "Gap" alone is not.
- **Internal-only** — fails the compliance filter for public use (usually the written-vs-oral
  competitive rule). Still valuable — routes to `sales-enablement-assets` by default rather than
  being discarded.

## Recommended destination(s)

Always give the primary destination skill plus any skill(s) that need to load *alongside* it —
these aren't alternatives, they're both needed. Example: a competitor-informed blog angle isn't
just `blog-writing-methodology` — it's `blog-writing-methodology` + `competitive-intelligence`,
because the blog skill doesn't own the compliance boundary on competitor framing, the
competitive-intelligence skill does.

## Unrouted flag

Set this whenever the ideal format has no dedicated skill — don't silently absorb it into the
closest available skill just to have somewhere to put it. An unrouted idea is a signal that a
new format skill might be worth building, not a failure of triage.
